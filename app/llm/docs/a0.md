# A0: English char-GRU on 200Pro+ (CPU path)

This is the first working slice of the A0 plan: a 56K-parameter English char-level
GRU that runs on the RV32IM core, with a UART line protocol.  Language scope is
English only: there is no Chinese tokenizer, corpus or evaluation in this path.  It deliberately does
not use miniTensor yet; the next iteration moves the two GEMVs onto the
accelerator and compares token-for-token against the same integer golden.

## Model

| item | value |
|---|---|
| corpus | TinyShakespeare, 1.1 MB, vocab 65 |
| structure | Embedding(65,64) -> GRU(64,96) -> Linear(96,65) |
| params | 56,480 |
| val loss | 1.67 (3,000 steps, Adam 3e-3, batch 128, seq 64) |
| weights | int8, per-output-channel scale, embedding int16 with scale, biases int32 Q15 |
| state | int16 Q15 hidden (96 values), sigmoid/tanh 256-entry LUT (Q4.4 input) |
| size | 62 KB weights, 80.5 KB firmware image |

The integer forward is the reference: Python (tools/gru_int.py) and C
(lm_soc/firmware/app/llm_model.c) produce the same 40-token greedy stream
(0/40 mismatches).  Per-output-channel int8 scales lift the match with the float
model from 13/40 to 17/40 and make the text less repetitive; that is still the
expected ceiling for 8-bit weights on a 56K model.

## Memory / speed

CPU GEMV is two int8 matrix-vector products per token (64x288 and 96x288) plus a
65x96 head: about 56K MAC/token.

**CPU baseline measured on the board (2026-11-01):** first build 100 chars in
191,182,095 cycles (1.91M cycles/char, 14 char/s).  Copying the 62 KB weight
tables into the 64 KB scratch gave 15 char/s; packing four int8 weights and four
int16 activations per 32-bit load gave 1.56M cycles/char, 17 char/s.  The per-row
quantisation keeps that speed.  The core data path is uncached, so loads dominate.

## miniTensor INT8 path

The throughput path moves the three GEMVs to miniTensor:

- tensor_gemm_core.sv: RUN_CYCLES 10 -> 8 (bit-exact on the board);
- int8 weights packed as [output group][k group][4 k][4 out];
- A tile is row-major, row 0 = x[4t..4t+3], rows 1..3 zero;
- one flat MT_GEMM burst per 4 output channels, accumulate across k;
- first k-group writes C (acc=0), the rest accumulate (no zero-fill DMA);
- 32 C tiles are buffered, then stored 4 rows at a time;
- gate math uses 32-bit multiplies/divisions; int64 only where it can overflow.

Results:

| gate | result |
|---|---|
| host C/Python golden | 0/40 mismatches |
| board selftest (MT vs Python golden) | 0/40 mismatches PASS |
| board throughput | **100 chars in 26,038,397 cycles = 103 char/s @27MHz** |

The INT8 activation path is faster but lower quality than the int16 CPU path:
its greedy text is "to thor to thor..." (the int16 path matches float 17/40 and
produces "I will the seal the world...").  This is the expected speed/quality
tradeoff; QAT or an int16 split would recover quality without changing the
miniTensor dataflow.

## Interactive layer (quality-first)

The 52K char GRU and the 66K word GRU were both trained on a 149-pair synthetic
English chat corpus.  Both overfit quickly (train loss 0.08-0.15, val 0.44-0.72)
and answer the wrong intent on held-out prompts, so they are not a reliable
interactive demo.

For a reliable "simplest interaction", firmware/app/chat_rule.c implements a
small rule/template chat layer:

- greeting / identity / capabilities / thanks / goodbye;
- name capture: "my name is alice" then "hello" -> "hello, alice!";
- "what is my name" reads the stored name;
- FPGA/CPU/language-model/weather/time/joke/where/learn answers;
- unknown input -> "i am not sure. try: ...".

Responses are paced at 20 characters/s (50 ms per character) so the output is
easy to read; the rule layer itself is instant.  Firmware is 13 KB and was
tested on the board:

    you: hello
    bot: hello! how can i help?
    you: who are you
    bot: i am a tiny chat program on an fpga.
    you: my name is alice
    bot: nice to meet you, alice.
    you: what is my name
    bot: your name is alice.

Build/upload:

    cd app/llm
    bash tools/build_fw_rule.sh
    powershell -ExecutionPolicy Bypass -File tools/program_board.ps1 -Bitstream build/pango/soc/prj_tasks/pnr_1/generate_bitstream/board_cpu.sbit
    powershell -ExecutionPolicy Bypass -File tools/upload.ps1 -Port COM9 -File build/fw/lm_rule.bin

Test several turns:

    powershell -ExecutionPolicy Bypass -File tools/chat_lines.ps1 -Port COM9 -Lines "hello|who are you|my name is alice|what is my name|bye"

Type interactively from a PowerShell window:

    powershell -ExecutionPolicy Bypass -File tools/chat_interactive.ps1 -Port COM9

Then type at the "you" prompt and press Enter. Type quit to exit. A normal
serial terminal (PuTTY / sscom, COM9, 115200 8N1) works too: the firmware echoes
characters and answers each line.

## Hybrid intent classifier

The rule layer was extended with a bag-of-words/bigram intent classifier:

- 20 intents (greeting, identity, capabilities, FPGA/CPU/LLM, weather, time,
  joke, location, learning, sad/happy, affirm/deny, name, fallback);
- 210 short English examples, stemmed token unigrams + adjacent bigrams;
- multinomial logistic regression, int16 weights (448 features, ~19 KB);
- held-out accuracy of the classifier alone: 82.2% (37/45);
- high-precision keyword rules run first, so common/ambiguous inputs
  (hello, good night, what is up, jokes, llm, upset, take care, wonderful)
  are handled exactly;
- ambiguous/low-margin classifier results fall back to "i am not sure";
- firmware size 39.3 KB, output paced at 20 chars/s.

Board-verified paraphrases (2026-11-01):

    you: howdy                    -> hello! how can i help?
    you: what is up               -> i am fine, thank you.
    you: can you tell me a joke   -> why did the chip cross the board? ...
    you: what does fpga stand for -> an fpga is a field programmable gate array.
    you: i feel unhappy           -> i am sorry to hear that. ...
    you: call me bob              -> ok, i will call you bob.
    you: hello                    -> hello, bob! how can i help?
    you: take care                -> goodbye! have a nice day.
    you: where is the fpga        -> i live inside an fpga.
    you: i feel wonderful         -> that is great to hear!
    you: that is right            -> ok.
    you: nah                      -> ok, no problem.

## Teacher distillation experiment

To move beyond the synthetic corpus, Qwen2.5-0.5B-Instruct was downloaded to
F: (943 MB weights, tokenizer, config) and run on CPU through transformers:
160 short teacher dialogues were generated into data/teacher_train.txt /
teacher_val.txt.  A 205K-parameter H112 seq2seq student was trained on the
teacher dialogues plus the 20K synthetic corpus; its int8 image is 194,856 B.

Blockers found:

- the runtime image is 192 KiB, but a 194 KB image is rejected by the loader;
  the 189 KB variant also failed even after rebuilding the boot ROM with a
  480 KiB loader now builds and accepts the 381 KB CPU tutor image;
- the CUDA torch install on F: stalls on the 9p filesystem for the 768 MB
  wheel; Qwen therefore runs on CPU here (about 1-2 s per short dialogue);
- the board was restored to the 127,688 B rank-31 image for demo use.

The teacher/student scripts are committed:
tools/gen_teacher_qwen.py, tools/gen_teacher_batch.py,
tools/normalize_teacher.py, tools/make_distill_data.py,
tools/train_attention_seq2seq.py.

A compact H88 distilled student was then trained and deployed:

- 107K parameters, teacher + synthetic corpus, vocab 250, rank-24 head;
- int8 bin 118,168 B, fits the 128 KB image;
- board test (2026-11-01):

    you: hello
    bot: hello bob! have a nice to meet you.
    you: what is a cpu
    bot: the cpu is the brain of a computer.
    you: what is the weather
    bot: the weather is cloudy.
    you: my name is alice
    bot: hello alice!
    you: how are you

The student still confuses some topics and emotions; the teacher set is only

## CPU / computer-organization QA (new domain model)

A separate domain model was built from a self-authored fact set rather than
the synthetic chat corpus:

- 10,475 CPU / computer-organization entries (8,685 facts + 1,790 aliases), key/overlap lookup only (ALU, pipeline hazards, caches,
  ISA, RISC/CISC, interrupts, DMA, TLB, coherence, Tomasulo, MSHR, MESI,
  DVFS, scatter-gather DMA, plus this SoC's ARES-L core, memory map, UART,
  and miniTensor 4x4 INT8 array / UB / VPU / DMA, ...);
- 16 question paraphrases per concept; classifier train/val split by
  paraphrase (12 train templates, 4 unseen val templates);
- hashed bag-of-words + bigram logistic classifier, int8 weights;
- exact concept-key lookup first, classifier as paraphrase fallback;
- held-out template accuracy: 94% (880/936);
- word boundary key matching plus token overlap fallback for missing words;
- threshold fallback: unknown questions print
  "i do not know that cpu concept.";
- robustness: lower-case, filler words, word order, plural stripping, and
  aliases such as "central processing unit" -> cpu, "arithmetic logic unit"
  -> alu, "translation lookaside buffer" -> tlb;
- small dialogue layer: greeting, "how are you", thanks, goodbye,
  "who are you", name capture, comparison questions, and follow-ups such as
  "how does it work" / "tell me more" on the last concept, with a
  per-concept detail sentence when available;
- board firmware 638,076 B, 20 chars/s output with per-answer TPS/time stats (key/overlap lookup).
- UART RX ring buffer polls during paced output; normal question/answer is
  stable, but very fast type-ahead can still overrun the 128-byte buffer.
- upload a 364 KB image with `-ListenSeconds 45`; a shorter listen closes
  the port while the UART is still shifting bytes and truncates the image.

Board examples (2026-11-01):

    bot: the cpu is the central processing unit that executes program instructions.

    you: explain the alu

    you: what is a cache miss
