# Y7：权重分块 —— 解除「整层权重必须装进 UB」的限制

> 这一轮本想做多尺度检测头（YOLO 最标志性的结构），先做了实验，**结论是它在当前
> 任务上不成立**，于是转向一个更硬、也更接近 YOLO 真实瓶颈的问题：宽层权重放不下。

---

## 1. 先说失败的实验：多尺度头

设计了双尺度检测器（stride-2 的 16×16 头负责小目标，stride-4 的 8×8 头负责大目标，
按目标尺寸分配监督信号）。训完实测：

| 目标尺寸 | head_s（16×16） | head_l（8×8） | 谁更好 |
| ---: | ---: | ---: | --- |
| 8 px | **0.46 px** | 1.03 px | head_s |
| 16 px | **0.35 px** | 1.23 px | head_s |

**细尺度的头在两种尺寸上都赢。** 我原本的推理是「16×16 的目标会覆盖整张 stride-2 图，
质心退化成图像中心」—— 这个推理是错的：16×16 的目标在 16×16 网格上覆盖 8×8 个格子，
是一块形状良好的斑块，质心就是目标中心，根本没有退化。

在 32×32 的输入上，粗尺度图就是单纯地太粗。既然多尺度在这个任务上不产生收益，
**加上去只是装饰**，所以没有采用，代码注释里保留了这个结论。

---

## 2. 真正的瓶颈：整层权重必须装进 UB

重构前的 `net_conv` 在算之前**一次性把所有输出组的权重行搬进 UB**：

```c
uint32_t nw_rows = ng * kk * nm;      /* UB_WT 只有 144 行 */
for (i = 0; i < nw_rows; i += 8) { mt_push(MT_LOAD, ...); }
```

也就是硬性要求 `ng·k²·nm ≤ 144`。换成 YOLO 的量级：

| 层 | 行数 | 需要 UB 行 |
| --- | ---: | ---: |
| 当前 demo 的 L3（16→16, 3×3） | 4·9·4 | 144 |
| YOLOv5n 常见层（256→256, 3×3） | 64·9·64 | 36864 |
| YOLOv5n 宽层（512→512, 3×3） | 128·9·128 | 147456 |

**这些层在原来的结构下根本无法表达** —— 不是慢，是写不出来。

---

## 3. 改法：按输出组分块

`net_conv` 外层增加一个**权重块**循环：搬入当前块的权重 → 算完这一块的所有输出组 →
搬下一块。层的权重总量从此与 UB 容量解耦。

块大小 `nmt` 由打包器按 UB 预算算出，**写进配置行第 5 字节，固件读回来**：

```c
nmt = max(1, min(nm, 144/(k*k*ng), 68/(ntiles*4)))
```

两条约束分别是 UB_WT 的 144 行，以及 UB_C..UB_BIAS 之间留给 C 行的 68 行。
用「打包器算、固件读」而不是两边各算一遍，是为了不让同一套规则有两份实现。

权重内存布局随之改成**分块连续**：块 ti 占 `ntap*nmt` 行，行内是
`(ti*ntap*nmt) + q*nmt + j`，其中 `q = g·k² + ky·k + kx`、`j` 是块内组号。
固件每块只需一次连续 `MT_LOAD`。

### 向后兼容

对现有所有层，`144/(k²ng)` 和 `68/(4·ntiles)` 都 ≥ nm，所以 **`nmt == nm`，布局与原来
逐字节相同**。这一点是实测的：改成 tiled 打包后 `mt_conv`、`mt_net`、`mt_detect` 三个
既有测试仍然全绿。

## 4. 压力测试：mt_wide —— 9× UB 的层

一个 8×8×48 → 8×8×48 的 3×3 卷积：**1296 个权重行 / 20736 字节，是 UB_WT 容量的 9 倍**。
`nmt=1`，12 个块，每块 108 行。这个层在重构前是不可表达的。

```
miniTensor wide layer: 8x8x48 -> 8x8x48, k=3 (weights 20736 B).
  weight tile size nmt=1 -> 12 tiles of 108 rows each.
  staged wt checksum: all=002601e0 lane0=0002511d
miniTensor wide layer PASSED (3072/3072 bytes, 41941 commands, 4065473 cycles)
```

## 5. 定位过程（以及两个把我带偏的坑）

这个测试一度有 **16/3072 字节不符**：固定是第 8 组的第 0 个空间位置、第 0 个通道，
值恒为饱和值 `0x7f`。

### 根因：我自己的测试夹具里两个 scratch 块重叠

```c
#define WIDE_BIAS   0x8200u   /* 48 rows = 768 B -> 0x8500 */
#define WIDE_CFG    0x8400u   /*   <-- 落在 BIAS 内部！ */
```

`WIDE_BIAS` 覆盖 `0x8200–0x84FF`，而 `WIDE_CFG` 在 `0x8400`。
**第 8 组的偏置行正好从第 512 字节 (= 0x8400) 开始** —— 于是配置字
`0x00070001` 变成了第 8 组的偏置行 0。

epilogue 是「偏置行 r 加到 C 行 r」，而 C 行 r 对应空间位置 r —— 所以受影响的正是
**空间位置 0**；配置字只占第一个 32 位字，所以只有 **lane 0** 被污染。
`acc + 458753` 再右移 7 位必然饱和成 127。

这解释了我之前觉得最矛盾的现象：**数值与权重、激活完全无关** —— 因为污染源是配置字，
它只随 `mult/shift` 变化。

### 坑 1：陈旧的目标文件

中途我用 `pack_wide.py 8 24 24 3` 生成了新夹具，但固件仍然打印 `8x8x48 ... 20736 B`。
也就是说我前面若干次「实验」其实一直在跑旧的 golden，结论全部无效。
（后来确认 Makefile 的依赖跟踪是对的：`-MMD -MP` + `-include $(DEPS)`，生成的
头文件确实在 `.d` 里。问题出在我的重建流程，不是构建系统。）

**救了我的正是夹具启动时打印自己的几何与字节数** —— 现在这是每次运行的第一个
断言：固件报的几何必须和打包器刚生成的一致。

### 坑 2：把饱和值当成「数据无关的垃圾」

我一度把权重缩到 {-1,0,1}、激活缩到 [-8,8]（理论上限只有 13），硬件仍给 127，于是我
推断「硬件读到了垃圾」。这个推断方向是对的，但我没继续问**「什么值是不随数据变化的」**
—— 答案就是配置字。

### 预防：编译期不重叠断言

现在 `mt_wide.c` 里有一组编译期断言，块挨着块逐一校验：

```c
#define MT_SA(cond, tag) typedef char mt_sa_##tag[(cond) ? 1 : -1]
MT_SA(WIDE_BIAS + sizeof(wide_bias) <= WIDE_CFG, bias_ends_before_cfg);
...
```

这类错误从此变成**编译错误**，而不是运行时 16 个字节的谜题。

## 7. 下一步

1. 分块按输出组切，激活 A 行会被重复搬 `nm/nmt` 次。`mt_wide` 的 `nmt=1` 意味着 **108 倍**
   放大（41941 条命令里绝大部分是 A 行搬运），是明确的下一个性能优化点：可以让 `nmt`
   随 `ng` 自适应，或者在 UB 里做 A 行的多组复用。
2. 距离真实 YOLO 仍然差：前端导出（torch/ONNX）、residual/concat 调度、640×640 规模
   下的分块流水。
