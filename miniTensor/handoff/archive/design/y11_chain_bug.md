# Y11：多层真实 YOLO 链 —— 缺陷很可能在我的参考实现里，不在硬件

> **已解决，见 [y12_chain_fixed.md](y12_chain_fixed.md)。** 根因是新打包器的 golden 漏了
> 一次 `[h][w][c] -> [g][h][w][4]` 的布局转换；**硬件自始至终是对的**。

> Y10 记录了这个缺陷的症状。这一轮把它缩小到了一个**出乎意料的方向**：
> **硬件可能是对的，错的是我新写的那个 golden。**

---

## 1. 先排除了「几何相关」这个猜测

上一轮的线索是「32×32 通过、24×24 失败」，怀疑 ntiles=6 触发了某个隐含假设。

把分辨率改成 **16×16**（ntiles = 4/2/1，全是 2 的幂）：

```
conv0p    4096 bytes  MISMATCH (4013 bytes)
conv0     4096 bytes  MISMATCH (3720 bytes)
```

**同样失败，症状一模一样**（每条 A 行只有第 0 个像素对）。所以不是几何问题。

---

## 2. 关键实验：把两个打包器在**同一层、同一分辨率**下对比

`mt_yolo`（通过）和 `mt_yolocnn`（失败）用的是同一份 `net_conv`，但 fixture 来自两个
不同版本的打包器。让新版也生成 32×32 的 stem，然后逐字节比对：

```
weights    576 bytes,       0 differ
image     4096 bytes,       0 differ
bias       256 bytes,       0 differ
config      32 bytes,       0 differ
golden   16384 bytes,   15055 differ      <- 只有 golden 不一样
```

**权重、输入、偏置、配置全部逐字节相同，只有 golden 不同。**

而 `mt_yolo` 是拿**旧 golden**做的比对，并且**逐比特通过**（16384/16384）。
硬件是独立的一方，它和旧 golden 一致、和新 golden 不一致 —— **那新 golden 极可能是错的。**

也就是说：这两轮追的「多层链缺陷」，很可能根本不是硬件缺陷，而是**我新打包器里的参考实现写错了**。

---

## 3. 但还没定案

我写了第三个独立实现（直接从**打包后的权重行**解包再卷积，这个结果就是硬件应该产生的），
结果它**和两个 golden 都不一致**（vs 新 16011 差、vs 旧 8554 差）。

所以这个第三方实现自己也有 bug（最可能是权重的解包索引），**目前不能拿它当裁判**。
定案需要：把解包实现修对，让它能复现旧 golden —— 那就能确认新 golden 错在哪一行。

这个比对脚本已经存成 `integration/tools/diff_fixtures.py`，下一轮直接用。

---

## 4. 教训（这次是关于我自己的流程）

我花了两轮怀疑硬件，而**一次「新旧 fixture 逐字节对比」就能立刻把方向掉转过来** ——
这个检查只要一条命令。

正确的顺序应该是：**当新写的参考实现和已验证的旧实现结论冲突时，先证明新参考是对的，
再去怀疑硬件。** 我跳过了这一步，因为「新测试是旧测试的超集」这个直觉让我以为参考
实现是可信的。

这条和前面几轮的教训是同一个根：**验证手段本身也需要被验证。**
